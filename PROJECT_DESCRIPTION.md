# Описание работы проекта Listly

## Назначение проекта

`Listly` - это Android-клиент для ведения личной медиатеки. Приложение позволяет пользователю искать медиаконтент, добавлять фильмы, сериалы, аниме и игры в личный список, распределять элементы по папкам, отмечать статус прохождения или просмотра, добавлять избранное, заметки и оценки.

Важно: данный репозиторий содержит только клиентскую часть проекта. Приложение работает вместе с отдельным backend-проектом, где реализована серверная часть: авторизация, каталог медиаконтента, пользовательские списки, папки и хранение данных. Без доступного backend API приложение не сможет полноценно выполнять поиск, вход, регистрацию и работу с личной коллекцией.

По умолчанию Android-клиент обращается к backend по адресу:

```text
http://158.160.251.150:8080
```

При локальной разработке может использоваться совместимый backend-сервер, запущенный на другом хосте или в локальной сети.

## Основные функции приложения

### Авторизация и регистрация

Пользователь может создать аккаунт или войти в существующий. Для регистрации и входа приложение отправляет логин и пароль на backend:

- `POST /auth/register` - регистрация пользователя;
- `POST /auth/login` - вход и получение JWT-токена;
- `GET /health` - проверка доступности сервера.

После успешного входа JWT-токен сохраняется в `EncryptedSharedPreferences`, а логин пользователя - в обычных `SharedPreferences`. Токен используется для авторизованных запросов к пользовательским данным. При выходе из аккаунта сохраненные данные сессии удаляются.

### Каталог медиаконтента

В каталоге пользователь может искать медиапозиции по названию. Поиск выполняется через backend:

```text
GET /media/search?query=<строка>&limit=12&offset=0
```

Клиент получает список медиапозиций, преобразует JSON-ответ в доменные модели `MediaItem` и отображает карточки в Jetpack Compose UI. Для каждой позиции приложение также пытается сопоставить пользовательское состояние: добавлена ли позиция в readlist, есть ли статус, папки, избранное, заметка или оценка.

### Детальный экран медиапозиции

При выборе карточки открывается экран конкретного медиаэлемента. Данные элемента загружаются через:

```text
GET /media/{id}
```

На детальном экране пользователь может добавить элемент в readlist, убрать его из списка, изменить статус, избранное, оценку, заметку и папки.

### Readlist, или личный список пользователя

Readlist - это личная коллекция пользователя. Она загружается с backend через:

```text
GET /user-media
```

Приложение поддерживает:

- просмотр сохраненных медиапозиций;
- фильтрацию по типу контента;
- фильтрацию по папкам;
- сортировку;
- отображение статуса, избранного, заметки и оценки.

Добавление позиции в readlist выполняется через:

```text
POST /user-media
```

Удаление позиции из readlist выполняется через:

```text
DELETE /user-media/{id}
```

Изменение пользовательских параметров выполняется через PATCH-запросы к `/user-media/{id}` и связанным endpoint:

- `/user-media/{id}/status` - изменение статуса;
- `/user-media/{id}/favourite` - изменение признака избранного;
- `/user-media/{id}/folders` - изменение папок;
- `/user-media/{id}` - изменение заметки и пользовательской оценки.

### Папки

Пользователь может создавать собственные папки и группировать в них элементы readlist. Работа с папками выполняется через backend:

- `GET /folders` - получить список папок;
- `POST /folders` - создать папку;
- `PATCH /folders/{id}` - переименовать папку;
- `DELETE /folders/{id}` - удалить папку.

В приложении папки используются в каталоге, на детальном экране, во вкладке readlist и на отдельном экране управления папками.

### Статусы, избранное, заметки и оценки

Для сохраненного медиаэлемента пользователь может указать:

- статус коллекции: запланировано, в процессе, завершено, брошено;
- признак избранного;
- пользовательскую оценку от 0 до 10;
- текстовую заметку;
- одну или несколько папок.

Эти данные не хранятся только на устройстве. Они отправляются на backend и затем повторно загружаются при обновлении пользовательской коллекции.

### Настройки и тема приложения

В настройках пользователь может:

- посмотреть состояние авторизации;
- перейти к экрану входа;
- выйти из аккаунта;
- открыть управление папками;
- переключить светлую или темную тему.

Тема приложения хранится локально через `ThemeRepository`.

## Как реализована клиентская часть

### Технологический стек

Проект реализован как Android-приложение на Kotlin.

Основные технологии:

- Jetpack Compose - построение пользовательского интерфейса;
- Material 3 - визуальные компоненты;
- Navigation 3 - навигация между экранами и нижними вкладками;
- Elmslie / ELM-подход - управление состоянием экранов;
- Dagger - внедрение зависимостей;
- OkHttp - сетевые запросы к backend API;
- Coil - загрузка изображений постеров;
- EncryptedSharedPreferences - защищенное хранение JWT-токена;
- JUnit - unit-тесты.

### Архитектура

Приложение разделено на несколько слоев:

```text
Compose UI -> Store / Reducer / Actor -> Interactor -> Repository -> Backend API
```

UI-слой отображает состояние и отправляет пользовательские события. Основные экраны построены на Jetpack Compose:

- `AuthScreen` - вход и регистрация;
- `CatalogScreen` - каталог и поиск;
- `ReadlistScreen` - личная коллекция;
- `MediaItemScreen` - детальная карточка;
- `SettingsScreen` - настройки;
- `FolderManagementScreen` - управление папками.

Для основных экранов используется ELM-подход. Пользовательское действие превращается в `Event`, reducer обновляет `State` и при необходимости создает `Command`, actor выполняет асинхронную работу, а результат возвращается обратно в store как внутреннее событие.

### Repository-слой

`AuthRepository` отвечает за:

- регистрацию;
- вход;
- сохранение и очистку JWT-токена;
- хранение логина;
- выбор base URL backend;
- проверку доступности backend.

`MediaItemRepository` отвечает за:

- поиск медиаконтента;
- загрузку конкретной медиапозиции;
- загрузку readlist;
- добавление и удаление элементов readlist;
- обновление статусов, папок, избранного, оценок и заметок;
- загрузку, создание, переименование и удаление папок;
- хранение текущего snapshot медиапозиций и папок в `StateFlow`.

`ThemeRepository` отвечает за локальное хранение выбранной темы.

### Interactor-слой

`MediaItemInteractor` содержит бизнес-логику операций над медиапозициями. Например, если пользователь выбирает новую папку, которой еще нет на backend, interactor сначала создает папку через repository, затем обновляет медиапозицию уже с backend-id этой папки.

Такой слой нужен, чтобы UI и Store не знали подробностей backend-операций и не собирали сложную последовательность запросов вручную.

### Сетевая интеграция

Запросы выполняются через OkHttp. Для авторизованных операций в запрос добавляется заголовок:

```text
Authorization: Bearer <jwt-token>
```

Данные передаются в формате JSON. Клиент вручную парсит ответы backend в доменные модели приложения. Retrofit подключен как инфраструктурная зависимость, но текущая реализация сетевых запросов использует OkHttp напрямую.

Для изображений используется Coil. В `AppModule` настроен `ImageLoader`, который использует OkHttp и DNS-over-HTTPS fallback для более стабильной загрузки постеров.

## Связь с backend-проектом

Backend-проект является обязательной частью общей клиент-серверной системы Listly. Android-приложение не содержит серверной логики, базы данных каталога и пользовательских коллекций. Оно выступает мобильным клиентом, который отправляет запросы к backend и отображает полученные данные.

На стороне backend должны быть реализованы:

- API авторизации и регистрации;
- выдача JWT-токена;
- каталог медиаконтента;
- поиск по каталогу;
- хранение пользовательского readlist;
- хранение статусов, папок, избранного, заметок и оценок;
- endpoint для папок;
- доступность сервера по сети для Android-устройства.

Для локального запуска backend должен слушать внешний интерфейс, например `0.0.0.0:8080`, а не только `127.0.0.1`, иначе реальный телефон не сможет подключиться к серверу.

## Навигация приложения

При запуске приложение проверяет наличие сохраненного JWT-токена:

- если токена нет, открывается экран авторизации;
- если токен есть, открывается основной экран с нижней навигацией.

Основные вкладки:

- `Каталог` - поиск и просмотр медиаконтента;
- `Мои списки` - пользовательский readlist;
- `Настройки` - тема, авторизация и папки.

Детальная карточка медиапозиции открывается поверх основного сценария. Управление папками открывается из настроек.

## Хранение данных

Локально на устройстве хранятся только служебные данные:

- JWT-токен в `EncryptedSharedPreferences`;
- логин пользователя;
- выбранная тема;
- optional override backend base URL.

Каталог, readlist, папки, статусы, заметки и оценки являются серверными данными и загружаются через backend API.

## Тестирование

В проекте есть unit-тесты для отдельных правил и преобразований:

- подготовка и валидация логина и пароля;
- правила навигации авторизации;
- подготовка названия папки;
- отображение ошибок;
- mapping backend-значений для типов медиаконтента и статусов;
- формирование заголовка авторизации;
- политики отображения каталога, readlist и настроек.

Для ручной проверки проекта используется end-to-end сценарий:

1. Запустить приложение.
2. Зарегистрироваться или войти.
3. Выполнить поиск в каталоге.
4. Открыть карточку медиапозиции.
5. Добавить ее в readlist.
6. Назначить статус, папку, избранное, заметку или оценку.
7. Проверить, что элемент появился во вкладке `Мои списки`.
8. Перезапустить приложение и убедиться, что данные подтянулись с backend.

## Ограничения

- Приложение зависит от доступности backend API.
- Offline-first режим не реализован.
- Серверная часть не входит в данный Android-репозиторий.
- Если backend недоступен, авторизация, поиск, readlist и папки работать не будут.
- Для полноценной проверки нужен либо публичный backend, либо локальный backend, доступный Android-устройству по сети.

## Итог

Listly реализован как мобильная клиентская часть клиент-серверного проекта. Android-приложение предоставляет пользовательский интерфейс, навигацию, управление состоянием, локальное хранение сессии и интеграцию с backend API. Backend-проект отвечает за серверные данные и бизнес-операции, а Android-клиент отображает эти данные и отправляет пользовательские изменения обратно на сервер.
